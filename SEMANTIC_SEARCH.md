# Семантический поиск «Альфа-Курс»

`SemanticSearch` работает независимо от BM25F: локальная BGE-M3 создаёт dense
векторы размерности 1024, PostgreSQL с pgvector ранжирует их по косинусной близости.
Предобученную модель не нужно обучать, платных API нет. Чужой backend и исходные
таблицы не изменены. BM25F продолжает работать по прежнему интерфейсу.

## 1. Зависимости

Python 3.11+, Docker для существующей PostgreSQL или собственная PostgreSQL 17
с установленным pgvector. Все команды выполняются из корня текущего проекта:

```sh
cd /Users/sev.olesya/Desktop/alfa
python3 -m venv .venv  # только если окружение ещё не создано
.venv/bin/python -m pip install -r requirements-semantic.txt
```

Установка sentence-transformers также устанавливает PyTorch и его зависимости.
Загрузка самих весов BGE-M3 — отдельный шаг: потребуется несколько гигабайт
на диске и время на скачивание. При первом поиске/индексации модель загружается
лениво, поэтому лучше заранее выполнить команду `model`, описанную ниже.
Обычные тесты модель не скачивают и используют отдельные небольшие зависимости.

## 2. pgvector и существующая БД

В исходном `postgres:17` нет серверных файлов pgvector. Подготовлен override,
который меняет только образ существующего сервиса db на `pgvector/pgvector:pg17-trixie`
и сохраняет тот же том `alfa_pgdata`, порт, имя контейнера и базу:

```sh
docker compose -f compose.yaml -f compose.pgvector.yaml up -d db
```

Команда перезапустит контейнер БД на образе с той же основной версией PostgreSQL 17.
Вариант Trixie сохраняет версию системной локали, с которой создан текущий том.
Не выполняйте `down -v`: это удалит данные тома. В дальнейшем для запуска этой БД
используйте оба compose-файла, чтобы не вернуться к образу без pgvector.
Для PostgreSQL вне Docker установите pgvector на сервере по официальной инструкции
для своей ОС и версии PostgreSQL. Рекомендуется pgvector 0.8+.

Настройте подключение без записи пароля в Python-код:

```sh
export DATABASE_URL='postgresql://USER:PASSWORD@localhost:5437/alfa_course'
.venv/bin/python -m alfa_search.semantic migrate
```

Миграция `alfa_search/migrations/002_semantic.sql` включает расширение `vector`
в `public` и создаёт только `search.material_embeddings` и
`search.semantic_index_state`. Существующие таблицы BM25F не меняются.
Для миграции нужны права включения расширения и создания таблиц. При отсутствии
серверных файлов, расширения или нужных прав возвращается `MissingPgvectorError`
с инструкцией. Миграция не загружает модель и не индексирует каталог.

## 3. Загрузка локальной модели

```sh
# Необязательно: выберите каталог кэша; используйте его и при индексации, и в API.
export SEMANTIC_MODEL_CACHE="$PWD/.model-cache"

# На Apple Silicon автоматически выбирается MPS, иначе CPU (или CUDA при наличии).
# Для ограничения нагрузки или проблем с MPS можно явно задать CPU:
export SEMANTIC_DEVICE=cpu

# Эта команда впервые скачивает большую модель, затем только загружает из кэша.
.venv/bin/python -m alfa_search.semantic model
```

Используется `BAAI/bge-m3` и фиксированный commit
`5617a9f61b028005a4858fdac845db406aefb181`, чтобы обновление ветки main не меняло
поиск незаметно. `SEMANTIC_MODEL_REVISION` может задавать другой полный commit SHA;
после смены версии требуется `update`. После скачивания можно запретить доступ к
Hugging Face:

```sh
export SEMANTIC_OFFLINE=1
```

Один экземпляр класса загружает модель один раз и переиспользует её. Создавайте
один экземпляр на процесс backend, а не на запрос. При нескольких worker-процессах
каждый имеет собственную копию модели в памяти. Вычисления выполняются через
`asyncio.to_thread` и сериализуются для экземпляра модели; event loop не блокируется.

## 4. Построение и обновление

```sh
.venv/bin/python -m alfa_search.semantic build --batch-size 8
.venv/bin/python -m alfa_search.semantic update --batch-size 8
```

Первый запуск рассчитывает векторы всех доступных материалов. Повторный запуск
обеих команд обрабатывает только изменения. Каталог читается серверным курсором
и обрабатывается пакетами. Неизменённые векторы не пересчитываются: сравниваются
SHA-256 полного подготовленного текста, имя модели, её commit и подпись настроек
кодирования. Новый материал добавляется, изменённый обновляется, исчезнувший или
недоступный удаляется из векторного индекса. Логи показывают processed/encoded/reused
и случаи обрезания текста. В базе не хранятся JSON-выгрузки или полные тексты.

Вся индексация выполняется одной транзакцией: ошибка любого пакета откатывает
все изменения. Advisory lock сериализует писателей. Поиск в read-only транзакции
видит согласованную версию индекса. Смена модели приводит к пересчёту всех векторов;
поиск с несовместимой моделью или политикой отбора вызывает `ModelMismatchError`
до вычисления embedding запроса. Отдельная таблица состояния позволяет проверить
это без чтения всех векторов. Обновление нужно вызывать после изменений каталога
или по расписанию, оно не запускается автоматически при поиске.

## 5. Поля, доступность и длина текста

Используется тот же `catalog_sql()` и те же настройки доступности, что у baseline:
опубликованные и неудалённые материал и ContentSettings; исключены `IsClosed=true`
и статьи с `IsPublic=false`. Связь строится по EntityId и EntityTypeId, удалённые
справочники не участвуют. Эти правила ранее согласованы для проекта. `Published`
не является обязательным фильтром: у документов NULL, у вебинаров поля нет.
Пара `(material_type, material_id)` сохраняется; реальный ID — UUID.

Текст содержит только название, описание, темы, теги и отрасли. HTML очищается,
пробелы нормализуются, повторяющиеся названия справочников удаляются. Регистр,
словоформы, стоп-слова и значимые термины сохраняются. BM25-лемматизация не вызывается.
Для приоритета информации порядок текста такой: «Название», «Темы», «Теги»,
«Отрасли», «Описание». Пустые поля пропускаются.

У модели предел 8192 токена. Для первой версии выбран лимит **2048 токенов**,
включая специальные, чтобы снизить затраты памяти и времени на локальном CPU/MPS.
Перед encode текст проверяется токенизатором модели. При превышении берётся
помещающийся префикс, повторно проверяется его длина; таким образом сначала
сохраняются название и метаданные, затем начало описания. Если сами метаданные
длиннее бюджета, их хвост тоже обрезается. Это явный компромисс первой версии.
Лог содержит ID и исходную/использованную длину; в строке БД сохраняются
`original_tokens`, `used_tokens`, `truncated`. Хеш считается по **полному** тексту,
поэтому изменение обрезанного хвоста также обнаруживается.

При необходимости задайте `--max-tokens 8192`, но учитывайте рост расхода памяти.
Лимит входит в подпись индекса: используйте одинаковое значение при индексации,
запросах и загрузке модели. Изменение лимита требует обновления индекса. Запрос
обрабатывается с тем же лимитом, его обрезание также логируется.

## 6. Поиск и интеграция в API

```sh
.venv/bin/python -m alfa_search.semantic search 'Как привлечь новых клиентов?' --top-k 10
.venv/bin/python -m examples.semantic_usage 'Как увеличить продажи?'
```

Публичный интерфейс:

```python
from alfa_search import SemanticSearch, SemanticConfig

semantic = SemanticSearch(config=SemanticConfig(batch_size=8, max_tokens=2048))

# Выполняются отдельной задачей, не в обработчике запроса:
await semantic.migrate()
await semantic.build_index()
await semantic.update_index()

# Сервисный слой общего API вызывает только search:
results = await semantic.search("Как привлечь новых клиентов?", top_k=50)
# [{"material_id": UUID("..."), "material_type": "article", "score": 0.87}, ...]
```

В FastAPI создайте экземпляр при инициализации приложения, передайте его через
существующий механизм dependency injection в сервис рекомендаций и вызывайте
`await semantic.search(...)`. Нового endpoint в этом проекте нет. UUID сериализуется
в строку на границе API. SQL параметризован. Сравнение векторов выполняется в БД:
`1 - (embedding <=> query_embedding)` возвращает косинусную **близость**, а не
расстояние. HNSW/IVFFlat не создаются — используется точный поиск.

Результаты сортируются по убыванию близости, при равенстве — по типу и UUID.
Возвращается не более top_k результатов без дублей. Пустая строка и top_k <= 0
дают `[]`; нецелый top_k и query другого типа вызывают TypeError. Пустой созданный
индекс даёт `[]` без загрузки модели; отсутствие миграции — понятную ошибку.
Ошибки подключения не подменяются пустой выдачей. Косинусная близость имеет диапазон
от -1 до 1, поэтому возможны нулевые и отрицательные оценки; порог релевантности
в этой версии не вводится. Шкала несопоставима с BM25F: оценки не складываются.

## 7. Тесты

```sh
.venv/bin/python -m pip install -r requirements-test.txt

# Без модели и без обязательной БД; интеграционные тесты будут явно skipped.
.venv/bin/python -m pytest -q

# На PostgreSQL с серверными файлами pgvector, можно в той же БД:
export TEST_VECTOR_DATABASE_URL="$DATABASE_URL"
.venv/bin/python -m pytest tests/test_semantic_db.py -q

# Необязательно: проверка чтения реального каталога и совпадения ключей с baseline.
# Требует актуального BM25F-индекса в указанной БД.
export CATALOG_DATABASE_URL="$DATABASE_URL"
.venv/bin/python -m pytest tests/test_semantic_catalog.py -q

# Отдельный тест реального BGE-M3: только после осознанной загрузки большой модели.
export RUN_REAL_MODEL_TESTS=1
.venv/bin/python -m pytest tests/test_semantic_real_model.py -q
```

Обычные тесты используют mock-модель и не импортируют PyTorch. Интеграционные
тесты действительно сохраняют 1024-мерные векторы и считают cosine в pgvector,
создавая и удаляя только временные `semantic_test_*` схемы. Они могут включить
расширение vector в тестовой БД. Исходные материалы и рабочий индекс не изменяются.
Проверяются текст и дедупликация, размеры векторов, лимиты длины, однократная загрузка
модели, отсутствие блокировки event loop, ранжирование, составные ключи, обновления,
переиспользование, удаления, rollback и несовместимость версий.

Тесты с mock-моделью проверяют корректность системы, а не качество BGE-M3.
Большая модель и полный индекс автоматически не скачиваются/не строятся. После
запуска на реальной модели качество оценивается отдельно по размеченным запросам,
на одинаковом каталоге с baseline. Персонализация, гибридный поиск и LLM-оценка
не реализованы.

Официальные источники:
[карточка BGE-M3](https://huggingface.co/BAAI/bge-m3),
[SentenceTransformer](https://www.sbert.net/docs/package_reference/sentence_transformer/model.html),
[pgvector: установка и cosine](https://github.com/pgvector/pgvector),
[pgvector с asyncpg](https://github.com/pgvector/pgvector-python#asyncpg).
