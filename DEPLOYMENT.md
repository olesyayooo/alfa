# Перенос модулей поиска в GitLab и серверный backend

Код хранится в GitLab, PostgreSQL продолжает работать на существующем сервере.
Локальный дамп и Docker-том переносить для этого не требуется.

## Что включать в репозиторий

- `alfa_search/` — оба класса поиска и SQL-миграции.
- `requirements*.txt` — зависимости поиска и тестов.
- `examples/`, `tests/`, `pytest.ini` — команды запуска и проверки.
- Документацию, `.gitignore`, `.dockerignore`, `.env.example`.
- Из evaluation: запросы, промпт, инструкцию и компактный отчёт с метриками.

В `.gitignore` исключены окружение Python, веса модели, `.env` и его варианты,
дампы, служебные файлы macOS, кэши и локальные выгрузки evaluation с описаниями.
Они остаются на компьютере. Их исключение из Git не удаляет файлы.
Исходные результаты и оценки, необходимые для воспроизведения метрик, при
необходимости передаются отдельно как данные/артефакты, а не в runtime-образе.

`.dockerignore` предотвращает попадание этих же локальных файлов в контекст
сборки Docker. Она не заменяет `.gitignore`.

В `compose.yaml` больше нет пароля: локальные значения перенесены в игнорируемый
`.env`. Compose подставляет их из него. Для новой локальной копии создайте `.env`
из `.env.example` и задайте свои значения. Python сам `.env` не читает: переменные
нужно передать процессу через окружение или средствами существующего backend.

## Как добавить код в существующий GitLab-проект

Текущая папка на момент подготовки не является Git-репозиторием. Для существующего
проекта удобнее клонировать его, создать рабочую ветку и добавить туда модуль.
Если в backend уже есть requirements, compose, .gitignore или Dockerfile,
объедините изменения с ними — не заменяйте существующие файлы целиком.
`alfa_search` должен быть доступен для импорта Python из кода backend.

Пример последовательности в клонированном репозитории:

```sh
git switch -c feature/search
# Добавить модуль и объединить конфигурацию с существующими файлами.
git status --short
git add alfa_search examples tests requirements*.txt pytest.ini
# Документацию и изменения конфигурации добавить после просмотра diff.
git diff --cached --stat
git diff --cached
git commit -m "Add BM25F and semantic search"
git push -u origin feature/search
```

Команды показаны для случая, когда эти каталоги лежат в корне репозитория;
в существующем monorepo используйте путь вашего backend. `.gitignore` не убирает
файлы, уже добавленные в Git. Если секрет ранее был опубликован, его нужно заменить;
одного добавления в `.gitignore` недостаточно.

## Подключение к серверной БД

На сервере задайте `DATABASE_URL` реальным подключением:

```text
postgresql://USER:PASSWORD@DB_HOST:DB_PORT/DATABASE
```

Если backend и PostgreSQL находятся в одной Docker-сети, DB_HOST обычно равен
имени сервиса PostgreSQL, а DB_PORT — его внутреннему порту 5432. Например,
`db:5432`, только если сервис действительно называется `db`. `localhost` внутри
контейнера backend указывает на сам backend, а не на соседний контейнер БД.
Локальный порт 5437 не следует автоматически переносить в серверную конфигурацию.

Реквизиты храните в серверном env/secret-хранилище или GitLab Settings → CI/CD →
Variables. При использовании CI значения нужно явно передать в развёртываемый
контейнер: наличие переменной в GitLab само по себе не меняет уже работающий сервис.
Пароль внутри DATABASE_URL должен быть URL-кодирован, если содержит специальные символы.

Не запускайте локальные compose-файлы вместо существующего серверного compose:
они описывают локальную БД. В серверной PostgreSQL должны быть серверные файлы
pgvector и включено расширение vector. При смене образа БД сохраняйте совместимость
основной версии PostgreSQL и версии локали/базового дистрибутива с существующим томом.
Локальный вариант pg17-trixie выбран под нашу локальную БД, а не под неизвестный сервер.

## Подготовка backend и индексов

В существующем Dockerfile backend добавьте установку зависимостей из
`requirements-semantic.txt` вместе с его собственными зависимостями и копирование
`alfa_search/`. Требуется Python 3.11+. Локальную `.venv` копировать нельзя: на
Linux зависимости устанавливаются заново. В runtime-контейнер передайте:

```text
DATABASE_URL=подключение_к_серверной_БД
SEMANTIC_MODEL_CACHE=/var/cache/alfa-models
SEMANTIC_DEVICE=cpu
SEMANTIC_OFFLINE=0
HF_HUB_OFFLINE=0
OMP_NUM_THREADS=2
```

Каталог `/var/cache/alfa-models` подключите как постоянный том с правом записи.
При первом запуске с доступом к Hugging Face один раз загрузите модель; затем
можно установить оба флага OFFLINE в 1. Версия модели зафиксирована в коде.
Веса в Git не нужны, но их кэш должен сохраняться между пересозданиями контейнера.

Если на сервере ещё нет готовых индексов, из окружения/контейнера backend выполните:

```sh
python -m alfa_search build
python -m alfa_search.semantic migrate
python -m alfa_search.semantic model
python -m alfa_search.semantic build --batch-size 2
```

Первая команда создаёт только таблицы BM25F в search и строит лексический индекс.
Миграция semantic включает vector и создаёт отдельные векторные таблицы.
Для миграций нужны соответствующие права БД. Исходные таблицы платформы не меняются.
Первоначальная загрузка модели потребует нескольких ГБ диска и время на индексацию.
Если серверные индексы уже построены по тому же каталогу и версии модели,
повторять это при каждом деплое не нужно. После изменений материалов вызываются
отдельные задачи update, а не индексация внутри пользовательского поиска.

Проверка из того же окружения:

```sh
python -m alfa_search search 'маркетинг' --top-k 5
python -m alfa_search.semantic search 'Как привлечь клиентов?' --top-k 5
```

Интеграция в сервисный слой API:

```python
from alfa_search import BaselineSearch, SemanticSearch

# Один раз на процесс backend, а не на каждый HTTP-запрос.
baseline = BaselineSearch()
semantic = SemanticSearch()

# В асинхронном обработчике или сервисе:
results = await semantic.search(query, top_k=10)
```

Это код модулей поиска, HTTP-endpoint здесь не создаётся. Каждый worker-процесс
загружает собственную модель, поэтому количество workers выбирайте с учётом памяти.

Официальные инструкции:
[переменные GitLab CI/CD](https://docs.gitlab.com/ci/variables/),
[сети и адреса сервисов Docker Compose](https://docs.docker.com/compose/how-tos/networking/).
