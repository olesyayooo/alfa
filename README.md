# Альфа-Курс: BM25F baseline

Оба алгоритма расположены симметрично в отдельных пакетах:

```text
alfa_search/
├── baseline/       # BM25F: service, repository, indexing, preprocessing, SQL и CLI
├── semantic/       # BGE-M3: service, repository, encoder, text, source и CLI
├── catalog.py      # общий SQL каталога и соответствие типов материалов
├── text.py         # общая очистка HTML
├── models.py       # Material и единый формат SearchResult
├── config.py       # настройки BM25F и общие правила доступности
└── migrations/     # отдельные миграции обоих индексов
```

Для интеграции в API используйте публичные импорты:

```python
from alfa_search import BaselineSearch, SemanticSearch
# Также доступны явные импорты:
from alfa_search.baseline import BaselineSearch
from alfa_search.semantic import SemanticSearch
```

CLI baseline доступен как `python -m alfa_search.baseline`; прежняя команда
`python -m alfa_search` сохранена. Semantic: `python -m alfa_search.semantic`.
Перенос файлов не требует переиндексации и не меняет формулы, веса или формат ответа.

Семантический поиск BGE-M3 + pgvector реализован отдельно:
[инструкция запуска и интеграции](SEMANTIC_SEARCH.md).

Независимый асинхронный Python 3.11+ класс `BaselineSearch` для подключения
к сервисному слою будущего backend. HTTP, FastAPI, embeddings и персонализации нет.
Индекс и статистика постоянно хранятся в PostgreSQL в схеме `search`.
JSON-выгрузки каталога нет.

## Установка и запуск

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
export DATABASE_URL='postgresql://USER:PASSWORD@HOST:PORT/DATABASE'

# Отдельный процесс первоначальной индексации, создаёт только search.*
.venv/bin/python -m alfa_search build

# Запрос использует готовый индекс, не загружает исходный каталог
.venv/bin/python -m alfa_search search 'Как привлечь клиентов?' --top-k 50

# После изменений материалов, статусов, тем или других индексируемых полей
.venv/bin/python -m alfa_search update
```

В локальном compose PostgreSQL доступен на `localhost:5437`, база `alfa_course`.
Учётные данные задавайте через окружение; модуль их не содержит.
Для установки индекса нужны права CREATE SCHEMA и записи в `search`;
исходные таблицы используются только для SELECT. Для запросов достаточно чтения
поисковых таблиц. SQL-миграция: `alfa_search/migrations/001_initial.sql`;
`build_index()` применяет её автоматически в той же транзакции, что и индексацию.

## Использование из Python

```python
from alfa_search import BaselineSearch, SearchConfig

baseline = BaselineSearch()  # DATABASE_URL; создать один раз в сервисном слое

# В отдельной задаче индексации:
await baseline.build_index()
await baseline.update_index()

# В обработчике запроса сайта:
results = await baseline.search("налоги", top_k=50)
# [{"material_id": UUID("..."), "material_type": "article", "score": ...}]
```

`material_id` — настоящий `uuid.UUID`, как в БД. Для JSON сериализуйте его в строку
на границе backend (пример: `examples/usage.py`). Результаты сортируются по score,
затем типу и UUID; пары `(material_type, material_id)` уникальны. Пустая строка,
только стоп-слова, неизвестные слова и `top_k <= 0` возвращают `[]`.
Повтор слова в запросе не меняет вес запроса; повторения в материалах сохраняются.

Конструктор не обращается к БД. Работа с PostgreSQL асинхронная через `asyncpg`;
каждый вызов открывает и закрывает своё соединение. CPU-предобработка выполняется
через `asyncio.to_thread`. Ошибки подключения и SQL передаются вызывающему коду,
ошибки индексации и поиска логируются. Если индекс отсутствует либо версия
предобработки/политика доступности изменилась, возникает `IndexNotReadyError`
из `alfa_search.baseline.repository`; нужно выполнить индексацию.

## Фильтры и проверенная схема источника

Индексируются строго `Title`, `Description` и названия из `Topics`, `Tags`,
`Industries`. Все пять категорий сохраняются отдельно. Содержимое статей и уроков,
транскрипции, SEO-поля и пользовательские данные не читаются.

`Id` материалов — UUID; `Title`/`Description` используют `citext`. Описание может
быть NULL. `ContentSettings` соединяется по `EntityId` **и** `EntityTypeId`;
на этой паре есть уникальный индекс, но нет полиморфного внешнего ключа.
Промежуточные таблицы справочников имеют составные PK и внешние ключи.

| Таблица | material_type | EntityTypeId |
|---|---|---|
| Courses | course | 8b440b1a-00c3-423a-9bae-3376475eb203 |
| Articles | article | 8ede4179-0faf-407d-a4fc-1d94f9a63089 |
| Documents | document | da1ad865-8605-4ab1-9f6c-4489a26fbc35 |
| Webinars | webinar | ece4acf3-5dd3-47b9-9f08-99c0d6203cc7 |
| Podcasts | podcast | 142c23e2-bf71-4a73-b12e-6b1b5e4d47cc |

Материал и `ContentSettings` должны быть неудалёнными и иметь проверенный статус
«Опубликовано» (`61f12dbc-3cd4-4c14-b64b-1709548b904e`). Удалённые значения
справочников исключаются. По согласованной политике дополнительно исключаются
`IsClosed=true` (кроме Documents, где поля нет) и статьи с `IsPublic=false`.
Эти правила настраиваются через `SearchConfig(exclude_closed=True,
public_articles_only=True)`; после их изменения индекс нужно перестроить.
`Published` не служит обязательным фильтром: у Documents все значения NULL,
у Webinars такого поля нет. Индекс отражает доступность на момент пересборки.

## Формула BM25F

Для слова t и материала d сначала объединяются нормализованные частоты полей:

```text
TF(t,d) = Σ_f weight_f * tf(t,d,f) / (1 - b_f + b_f * length(d,f) / avg_length_f)
IDF(t)  = ln(1 + (N - df(t) + 0.5) / (df(t) + 0.5))
score(d,q) = Σ_unique_t_in_q IDF(t) * (k1 + 1) * TF(t,d) / (k1 + TF(t,d))
```

`df` считает материалы, а не поля. `N` включает все индексируемые материалы;
средняя длина каждого поля считается по всему каталогу, включая нулевые длины.
У поля с нулевой средней длиной нет postings, поэтому оно не участвует в score.
Насыщение применяется **после** объединения частот полей.

Порядок параметров: `(title, description, topics, tags, industries)`.

```python
config = SearchConfig(
    weights=(3.0, 1.0, 2.0, 2.0, 1.5),
    b=(0.75, 0.75, 0.75, 0.75, 0.75),
    k1=1.2,
)
baseline = BaselineSearch(config=config)
```

`k1=1.2` задаёт насыщение частоты, `b=0.75` — умеренную нормализацию длины;
`b=0` отключает её для соответствующего поля. Веса, b и k1 можно менять без
переиндексации. Поиск выполняет два SELECT в согласованной read-only транзакции:
проверяет версию индекса, затем вычисляет BM25F и top-K в PostgreSQL только по
postings слов запроса. Score в таблицах не сохраняется.

## Предобработка и обновления

Общий `Preprocessor` очищает HTML, приводит текст к нижнему регистру, заменяет
`ё → е`, сохраняет русские/латинские/числовые токены и их частоты, убирает небольшой
список стоп-слов. Русские слова лемматизируются `pymorphy3`; числа, смешанные
термины и бизнес-аббревиатуры (`1С`, `B2B`, `НДС`, `CRM`, `SEO`, `ИИ`) сохраняются.
NULL и отсутствующие справочники дают нулевую длину поля.
Лемматизатор не исправляет опечатки и не добавляет синонимы:
«налог»/«налоговый» и «ИИ»/«искусственный интеллект» автоматически не объединяются.
После изменения алгоритма предобработки требуется пересборка; при изменении его
кода нужно повышать версию в `Preprocessor.signature`.

`update_index()` сейчас делает полную пересборку, а не инкрементальное обновление.
Для текущего небольшого каталога это обеспечивает точную статистику при любых
обновлениях, удалениях и смене статуса. Один SELECT читает согласованный каталог;
запись индекса выполняется одной транзакцией. Advisory lock сериализует запуски
индексации. DELETE с MVCC позволяет запросам видеть предыдущий полный индекс до
commit, затем новый. При ошибке все изменения, включая миграцию, откатываются.
Последовательность term_id может иметь пропуски после rollback — на выдачу это
не влияет. Обновление не запускается автоматически при поиске; его вызывает
отдельная задача после изменения каталога или по расписанию backend.

## Тесты

```sh
# Без БД: предобработка, частоты, поля и валидация параметров
.venv/bin/python -m unittest tests.test_preprocessing -v

# Контролируемый набор: создаёт и удаляет изолированные search_test_* схемы
export TEST_DATABASE_URL="$DATABASE_URL"
.venv/bin/python -m unittest discover -s tests -p 'test_*.py' -v

# Проверка рабочего индекса и показ top-5 на реальных данных
.venv/bin/python -m tests.integration

# Пример вызова из другого Python-модуля
.venv/bin/python -m examples.usage 'управление бизнесом'
```

Тесты проверяют BM25F по ручному расчёту, частоту и насыщение, IDF, длину описаний,
все пять полей, смену весов без индексации, совпадающие UUID разных типов, пустую
выдачу, идемпотентность, обновления/удаления, rollback после частичной записи и
согласованное чтение во время пересборки. Без TEST_DATABASE_URL тесты БД явно
пропускаются. Реальная проверка использует запросы «маркетинг», «налоги», «ИИ»,
«управление бизнесом»; это smoke-проверка, а не размеченный benchmark качества.
